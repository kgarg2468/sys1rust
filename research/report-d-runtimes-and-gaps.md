# Report D: cross-platform System One runtimes and gap analysis

Date: 2026-09-28. Scope: non-Apple and non-Rust runtimes, independent benchmarks, articles, and a gap analysis of what nobody has shipped. Every number below comes from a live source read today (GitHub via `gh`, web pages, HN Algolia API). Nothing is from memory. Where a source measured on a different machine or in a different session, the table says so. Self-reported means the runtime author published the number.

Companion reports cover Rust crates, Apple Silicon projects, and model internals. This report cites those areas only where a fact was needed for a verdict.

## 2. Benchmark verification

### kime RTX 4090 claim (2.61 ms vs 35.72 ms, 13.7x)

Verified with a caveat. The kime-bench report `reports/2026-09-28-kime-0.1.0-4090` gives W1 (one choice question on a support email) kime f16 p50 2.609 ms. The Laya number, 35.72 ms fp32, comes from the first report on the same box, not the same session. The ratio is 13.7x at p50 and 6.9x at p95 (5.255 ms). A same-session gate run on the same day gave Laya fp32 35.792 ms, Laya fp16 autocast 35.244 ms, kime f16 4.343 ms (8.1x) with p10 2.617 ms, and kime f32 6.087 ms. The gap between 2.6 and 4.3 ms is a Windows GPU time-slicing "slow phase": another process held 17 GB on the card. W3 (10 questions over a 512 token state) is 38.151 ms vs 54.24 ms (1.42x), 3.8 ms per question, and the same-session run gives 37.905 vs 54.808 ms (1.45x). Answers: kime f16 W1 matched Laya CUDA fp32 on 96/100 (max probability diff 0.0172), W3 498/500 (0.0893). 96/100 is below the 99% agreement this project requires. kime-bench's gate report says it is the same gap its first report found between Laya on CUDA and Laya fp32 on MPS. Against the MPS reference, kime matched 100/100 on W1 and Laya on CUDA 96/100 (checked 2026-09-29).

The kime CHANGELOG separately reports 2.62 ms p50 vs laya-serve 0.3.7 at 17.74 ms in one session on the 4090, so the Laya baseline varies 2x between kime's own documents (17.74 ms laya-serve HTTP vs 35.72 ms Laya Python direct). Take the 13.7x as an upper bound. The same-session figures are 6.8x (the CHANGELOG run against laya-serve) and 8.1x (the gate run).

Why W3 is only 1.4x: kime's own profile shows 5,120 tokens take 36 ms in GEMMs, 13.2 ms in attention, and 2.3 ms in everything else. That is about 3.77 TFLOP per call, or about 23 ms at 4090 f16 peak. No runtime trick closes that; only fewer tokens (encode the state once) or lower precision (FP8, which changed answers in two independent reports) does.

### Energy

kime PR #109 on the 4090 with the English model: kime FP16 0.73 J per decision one at a time (1.69 ms p50) vs Laya 0.3.9 bf16 autocast 2.41 J (16.4 ms p50); batches of 16: 0.57 J vs 0.85 J. kime FP32 2.02 J and 1.57 J; Laya FP32 3.22 J and 2.28 J.

### Other same-machine comparisons

- laya.cpp: native vs matching-precision Python on one RTX PRO 6000, separate runs, 0.0001 tolerance. Table in section 1.
- c4bbage/laya-serve: four stacks on one shared 4090 (Python FastAPI 73 rps, Go gateway + Python backends 193, goserve + ORT CUDA fp16 336 on two GPUs, goserve + TRT fp16 402) with argmax agreement on 4,436 questions.
- dev.to NVIDIA study: five backends across four GPUs with 74/74 parity rows and an SLO-based throughput metric.
- kevala: nine models in one browser on one M4 Max with accuracy on 2,592 calls.
- jayluxferro/laya-mlx-benchmarks (SSRN preprint): per-question p50 6.6 to 19.6 ms at 50 token states and 12.9 to 37.1 ms at 200 tokens on M4 Max; batching saturates at 8 to 16; six minute sustained load degrades throughput 36 to 77%; FP16 equals FP32 to 4 decimals.
- mizorewww/laya-mlx engineering report: compile, selected-Q, and a hand-written Metal GELU/gate kernel give 1.03 to 1.08x, "the tested engineering changes do not deliver 10x"; naive 8-bit and 4-bit backbone quantization slowed inference.
- Model-quality benchmarks that are not runtime benchmarks: ReflexBench (Laya base 35.1%, Jev 73.0%), instax-dutta/sysone-bench (byte-identical inputs, Jev 0.9065 vs Laya 0.6863), gazelle93/decision-models-under-pressure (Laya changes 49.4% of answers when options are reordered, Jev 14.6%), edgelesssys/privatemode-decisions-benchmark (Laya normalized 0.422), JevBench v1.4 (Laya adjusted p50 1.72 s on CPU, Von 0.34 s).

Every number in this section is self-reported by the runtime author except jayluxferro (independent of laya-mlx), decision-models-under-pressure, and the dev.to study (independent of upstream). The HF sora-2 blog put it plainly: "Almost every local number is self-reported... no two use the same request shape."

Architecture insights that recur across sources:

1. Each question is a separate row that re-reads the whole state, because attention is bidirectional and the state representation depends on the question. Upstream issue #49 (closed 2026-09-25) says true encode-once "needs a newly trained checkpoint... not planned for the open-source models". Upstream #109 and #343 tokenize the state once but still run K rows.
2. ModernBERT's window trap: HF builds the local window from sequence index while RoPE uses position ids. Upstream fast.py comments that `ModernBertAttention.sliding_window` is the inclusive flash-attn value and "must NOT be used", and uses `config.sliding_window` (local_attention // 2 = 64). kime spec 05 uses the same |pos_i - pos_j| <= 64 definition. ikken found the stock window flipped 8/20 answers under parallel positions.
3. Padding is the main waste for batching. c4bbage measured 28% of the token budget wasted on padding at batch 48 (24% at 16) and found smaller batches faster for that reason. kime's embedding path shows 9.8x from packing vs padding at max_length 512 and 1.5x at 16. laya-system-one pads to fixed lengths at about 4x waste on short inputs.
4. Quantization: per-channel weight-only INT8 and MatMulNBits kept every measured answer on the English checkpoint, but the multilingual MatMulNBits build flipped 1 of 16 in an independent check (Report B, section 7). Per-tensor or dynamic INT8 with quantized activations flips decisions and makes results depend on batch padding. FP8 and FP4 changed decisions in c4bbage (97.3% to 89.5%) and aaditagrawal. FP16 vs FP32 changes few decisions, but of the sources here only jayluxferro reports the two equal to 4 decimals. Report B (section 7) records a 0.009 worst probability shift for upstream's fp16 path, FluidInference's multilingual Core ML reports 0.0126 on the ANE (Report C, R2-3), and laya.cpp Core ML fp16 exceeded its 0.0002 tolerance. The base-M5 bake-off compared each fp16 path with the same runtime's fp32 path. MLX fp16 kept 100% agreement with a maximum probability shift of 0.014 on multilingual and 0.006 on typed-decisions. PyTorch MPS fp16 kept 99.5% and 99.8% with maximum shifts of 0.61 and 0.010. Those figures are in the precision table of `results/tables.md`, which arrives with the bake-off results in PR #5.
5. At batch 1 on a GPU the model is launch-bound, not FLOP-bound. Every sub-5 ms result (upstream TileLang, kime, aaditagrawal, laya.cpp) uses CUDA graphs per shape bucket plus fused attention and resident 16-bit weights. aaditagrawal adds a precomputed per-token table of normalized embeddings and the first QKV projection (491.9 MiB) and computes the head only at marker positions.
6. At many questions over a long state the model is GEMM-bound (kime W3: 36 of 51 ms in GEMMs). Only fewer tokens or lower precision helps.
7. HTTP servers with a fixed batching window pay the window at low load. c4bbage's 16 ms single-request latency is mostly its 10 ms window; laya.cpp uses 2 ms; kime dispatches when the worker is free.

## 5. Ranked opportunities for a solo developer

Ranked by how much speed is left on the table times how little competition has shipped.

### 1. Encode-once model plus runtime (state-first, block-masked, question towers)

Why it is the largest gap: every runtime today pays K full passes over the state for K questions. kime's W3 profile shows 10 questions over 512 tokens is GEMM-bound at about 23 ms of pure f16 math on a 4090, so no kernel work gets it below about 1.4x of Laya. An encode-once model turns K x S tokens into S + K x q tokens. ikken measured 13.7x on a 2,048 token state with 20 questions on a laptop CPU and 8.9x at 512 tokens, with per-question hidden states within 1e-7 of asking alone.

Why nobody has it: it needs a newly trained checkpoint. Upstream said it is not planned for the open models. ikken is a library with 0 stars, one-seed accuracy data (0.790 vs 0.752, with numeric questions worse), and no checkpoint. kime has the spec (05) and a trainer (kime-train, Burn, Metal, one Banking77 epoch in 33 minutes on the top 4 layers) but has not shipped kime-v1, and its cache and cross-attention kernels for it exist only in spec 08.

What a solo developer would build: fine-tune Laya (or Ettin/mmBERT) with ikken's parallel-position block mask and a marker head, publish the checkpoint with an agreement number against Laya on the parity sets, and ship a small runtime that caches the state encoding (K and V per layer) and runs question rows against it. The runtime piece is small compared with the training piece. Risks: training data (Laya's typed-decisions data is not confirmed public), accuracy on numeric and cross-reference questions, and kime landing first.

### 2. Same-machine cross-runtime benchmark harness with an agreement gate

Why: every published number is self-reported, request shapes differ, and even one project's numbers disagree with themselves (kime Metal on M4: 55.6 ms vs 74.1 ms MPS in the CHANGELOG, 103.67 ms vs 83.44 ms in kime-bench). Nobody has laya.cpp, kime, sys1, laya-mlx, laya-coreml, ONNX Runtime CPU/CUDA, TensorRT, Arbiter and upstream `fast=True` on one box with one request set. kime-bench already wrote down the right rules and a W1/W3-style workload set that others could adopt.

What to build: a harness that drives any `/v1/systemone` endpoint and in-process library with fixed W1/W3/W9-style requests, gates on answer agreement and probability drift against upstream fp32, records git and model hashes, and publishes raw Parquet plus p50/p95/p99 and energy where NVML or SMC is available. It is cheap (weeks, not months), it is the only way to know which runtime to build on, and it would become the reference others cite. It does not by itself make anything faster.

### 3. Apple-native engine that measurably beats MPS, MLX and Core ML at batch 1 and under load

Why: on Apple hardware nothing native has shown a clear win. kime Metal is level with or behind Laya MPS at batch 1 depending on the run and "part of the Metal pass still waits on the CPU". laya-mlx found MLX-level changes give 1.03 to 1.08x and did not try a varlen or window-aware attention kernel. laya-coreml reports about 5 ms for short decisions on M3 Max but slows at L1024 and silently fell to CPU at 78 to 82 ms in some runs; laya.cpp's Core ML lane uses 1.6 GiB fixed buckets and publishes no latency. Nobody routes short requests to the ANE and long ones to Metal, packs question rows without padding on Metal, and batches across requests with an answer cache in one binary. The other worker's Apple report covers the candidate stacks in depth; this item is here because the gap analysis supports it.

What to build: Metal varlen attention with the 64-position window and per-sequence RoPE positions, simdgroup GEMMs sized per bucket, one command buffer per batch, cross-request batching, and a measured crossover table between ANE buckets and Metal. Gate every kernel on the 625-question parity set. Risk: kime is already on this path and Apple performance work is hard to measure on a shared laptop.

Alternatives that did not make the top three: a Vulkan or ROCm window kernel for AMD and Intel (laya.cpp Vulkan is 0.44 to 1.14x Python on NVIDIA; nobody serves fast on non-NVIDIA discrete GPUs), and generalizing aaditagrawal's sub-2 ms CUDA path beyond SM120 with cross-request batching (kime already does 2.6 ms with determinism guarantees, so the headroom is about 1 ms).

Do not build: a response cache (kime has one), a CUDA batching server (laya.cpp, kime, c4bbage, sys1), CPU INT8 (upstream PR #498, kime INT8, edgejev), or a TensorRT export (c4bbage, nmcglo, dev.to study all have working exports and the fixes ModernBERT needs).

## 6. Open questions

2. alvarobartt/sys1 publishes no latency or throughput numbers. Its `src/batching.rs` and `models/modernbert.rs` exist but were not read in this pass.
3. laya.cpp's Core ML lane has no published latency; validation was on M1 Pro only.
4. kime's two M4 comparisons disagree (Metal faster than MPS in the CHANGELOG, slower in kime-bench). Load average was 20 to 58 in the CHANGELOG run.
