# Report C: Laya-class System 1 models on Apple Silicon (MLX, Core ML/ANE, Metal)

Date: 2026-09-28. Shard: "Round 2: MLX and Apple Silicon" plus the Apple items in "Round 3" of the earlier research notes (not in this repo). Target machine: base Apple M5, 32 GB, macOS 26.2.

Method: every number below was read today from the live source (GitHub API via `gh`, Hugging Face API via `curl`, Apple pages via fetch). Nothing is from memory. "Confirmed" means the source says exactly that. "Corrected" gives the value the source actually says. "Unverifiable" means no source found today.

Key fact that changes the reading of the earlier claims: almost every published Apple number comes from one of four lineages, and they are not interchangeable.

1. mizorewww (`laya-mlx`, `laya-coreml`): M3 Max, 40 GPU cores, 128 GiB, macOS 27.2. Python.
2. FluidInference (`laya-coreml` on HF, `FluidUse`, `decision-modernbert-base-coreml`, `laya-english-coreml`): M5 Pro, 24 GB, macOS 27.0. Swift.
3. tc3oliver/laya-apple: M4 Max, macOS 26.6.2, plus community runs on M4 Pro, base M4 (32 GB, macOS 26.2) and M2 Pro. Python.
4. afshinm/laya-mps: M5 Pro, 24 GiB, macOS 26.4. Python/PyTorch MPS.

No project publishes a base-M5 Laya number. The closest analogs are the base M4 run in laya-apple and kime's base M4 (10-core GPU) Metal run.

Note the LayaKit row: on M5 Pro the mizorewww CPU+GPU "general" bundle (4.83 ms) beat its ANE bundle (5.19 ms). That is a second independent M5 Pro measurement showing the ANE lead has closed.

## 3. Base M5 vs M5 Pro, and macOS 26.2

Apple's published specs:

| | Base M5 | M5 Pro |
|---|---|---|
| GPU cores | 10 (8 in some configs) | 16 or 20 |
| Neural Accelerators | one per GPU core, so 10 | one per GPU core, so 16 or 20 |
| Neural Engine | 16-core | 16-core, "faster ... with a higher bandwidth connection to memory" |
| Memory bandwidth | 153 GB/s | up to 307 GB/s |
| Max unified memory | 32 GB | 64 GB |
| Apple GPU family (Metal) | 10 | 11 |

Sources: https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/ ; https://www.apple.com/newsroom/2026/03/apple-debuts-m5-pro-and-m5-max-to-supercharge-the-most-demanding-pro-workflows/ ; https://en.wikipedia.org/wiki/Apple_M5 ; GPU family from https://github.com/AI-native-Systems-Research/scratchy/issues/118.

What that implies for Laya on the target machine:

1. ANE path. The Neural Engine core count is the same. The 3.6 ms L128 multilingual figure (M5 Pro, macOS 27.0) should transfer to the base M5 within the ANE's memory-connection difference, which Apple does not quantify. No one has measured it. laya-apple's base M4 (32 GB, macOS 26.2) run gives typed-decisions L128 on ANE at 14.54 ms vs 37.05 ms on MLX, a 2.5x ANE advantage on a base chip where the GPU is small. Expect the ANE lead to be larger on the base M5 than on the M5 Pro, because the ANE is unchanged and the GPU is half.
2. MLX GPU path. The per-question encoder forward is a matmul-heavy compute-bound workload at L128 to L512, so it scales with GPU core count and Neural Accelerator count. Expect roughly half the M5 Pro's throughput for batched work. Measured base-M5 peaks (macOS 27, Metal 4.1, scratchy issue #118, 2026-09-25): f16 matmul2d 15.3-16.6 TFLOP/s, int8 31-33 TOPS, fp8 not double-rate (16.4), stream read 124.6 GB/s.
3. Apple's own M5 vs M4 MLX numbers (MacBook Pro M5 24 GB vs M4): time-to-first-token 3.3-4x faster, decode 19-27% faster, bandwidth 153 vs 120 GB/s. Prefill-like work is where the base M5 gains over M4; a Laya forward pass is prefill-like.
4. Encoder models and the Neural Accelerators. Apple's page only discusses LLM prefill and decode. MLX's NAX kernels are general (`steel_gemm_fused_nax`, `steel_attention_nax`, `quantized_nax`), so every matmul in ModernBERT benefits. The fused NAX attention path is gated by head dim and mask type (PRs #3842 D256, #4455 D72/D80 unmasked, #4476 D256 causal); ModernBERT's head dim is 64 with a boolean window mask. Whether that combination takes the NAX attention kernel or the older steel kernel is unverified.
5. macOS 26.2 is enough for the Neural Accelerators. MLX v0.30.0 added them with "macOS >= 26.2"; macOS Tahoe 26.2 shipped the OS side. Two consequences on M5: fp32 matmul runs as TF32 by default (`MLX_ENABLE_TF32=0` restores fp32; Ollaya refuses to start without it), and MLX issue #3897 shows padded batched attention on M5 differs from single-sequence by about 2^-11 in fp16 (argmax unchanged), reproduced on a base M5 32 GB macOS 26.5.2 and an M5 Max, not on M3 Max. Parity tests that demand bit equality across batch sizes will fail on M5.
6. Core ML on 26.2 vs 27.0. All FluidInference ANE numbers are macOS 27.0; laya-apple's base M4 run on 26.2 shows ANE placement and parity working with coremltools 9.0. No source compares Core ML ANE latency across 26.2 and 27.x for the same model.
7. Build caveats. MLX no longer builds from source with Xcode 27 (issue #4533, open 2026-09-19); mlx-rs and Ollaya's MLX crate build MLX from source. mlx-sys `build.rs` sets no `CMAKE_OSX_DEPLOYMENT_TARGET`; Ollaya notes a target below 26.2 leaves out the NAX kernels. Whether a default mlx-rs build on macOS 26.2 includes NAX is unverified.
8. Metal 4.1 forward-progress features do not run on the base M5 (GPU family 10). Not relevant to Laya today; it matters only for custom persistent-kernel designs.

## 4. ANE constraints (verified)

1. Shapes. Core ML on the ANE takes static or enumerated shapes. mizorewww exports enumerated lengths from {16, 32, 64, 96, 128, 192, 256, 384, 512, 768, 1024}; `RangeDim` on GPU gave wrong results (47/63) and is rejected by default. FluidInference ships four fixed buckets (128/256/512/1024) and truncates on the right like `max_len`. laya-apple ships 64/96/128 (typed, laya) and 64/96/128/256 (multilingual).
2. Size per shape. 614 MB per fp16 bucket for the 322M multilingual model (FluidInference); about 700 MB per bucket for the 421M English model (laya-fast); 129-252 MB body only when the embedding table stays on the host (mizorewww). One process must map every loaded bucket.
3. Compile. 273.5 s cold on device for laya-apple's BC1S `.mlpackage` (cache 0.7-1.4 GB per bucket in the per-user Caches folder under `<process>/com.apple.e5rt.e5bundlecache/<macOS build>/`, keyed per executable and OS build, so it cannot be shipped); 4.9-8.5 s for FluidInference's precompiled `.mlmodelc`; about 20 s for mizorewww in-process.
4. Batching. Every shipped ANE artifact is B=1. Multi-question requests run one call per question.
5. Correctness. The ordinary SDPA graph is wrong on the ANE under strict gates (laya-apple: up to 85/187 mismatches; FluidInference English root 0.035 error vs 0.02 gate). The multilingual model passes a looser gate (0.0126) with a plain graph. 6-bit and 4-bit palettes fail parity on the ANE in every lineage; W8 k-means palette passes (mizorewww).
6. Silent fallback. `CPU_AND_NE` means allowed, not guaranteed. afshinm saw a Core ML export run entirely on CPU at 121.9 ms; laya-apple checks the compute plan at load and refuses artifacts that are not 100% ANE.
7. Length crossover. ANE wins only at short lengths because L x L attention grows faster on it: FluidInference L128 3.6 vs 3.9 ms, L256 9.9 vs 5.2 ms (M5 Pro); laya-apple crossover at 128 tokens for typed-decisions on M4 Max.
8. Energy. Only M3 Max data exists: 0.154 J (ANE FP16) vs 0.429 J (compiled MLX) per decision whole-system, 30.75 W vs 61.39 W mean. No M5 Laya energy measurement found. General ANE power across M1-M5 (Hoxton Macs, powermetrics, conv benchmark): about 11 to 19 TFLOPS.

## 6. What is genuinely unbuilt on Apple Silicon today

Each item was searched for counterexamples first (GitHub repository and code search, HF API, MLX issue tracker).

1. Native (Swift or Rust) server on MLX or ANE with cross-request multi-question batching and a `/v1/systemone` endpoint. Closest: sys1 and kime (Rust, batching, `/v1/systemone`, but candle or custom Metal, and kime is slower than PyTorch MPS on M4); andyjusa/laya-mlx-rs (mlx-rs, `/predict`, batching inside a request only); jevalaya (Rust, ANE native, MLX through PyO3, no batching).
2. Native ANE + MLX router. Exists in Python (laya-apple, laya-fast). In Rust only jevalaya, whose MLX half is Python-in-process.
3. MLX variable-length attention without padding. Not in MLX; laya-mlx pads to shape buckets. kime-metal packs sequences but is not MLX.
4. Fused sliding-window (ModernBERT local attention) kernel in MLX. MLX PR #3552 open since 2026-05-15, unmerged. Every MLX port uses a mask array. laya-fast has custom fused RoPE and GeGLU kernels in MLX, not attention. b0xtch/laya-candle has tiled attention in candle Metal.
5. ANE batching (B > 1) for Laya. None shipped. kime spec plans it; kime-ane is a stub.
6. Any Laya measurement on a base M5. laya-apple's community matrix lists M5 as "Wanted". No issue, README or model card in the surveyed repos mentions a base M5.
7. Energy per decision on any M5. Only M3 Max (mizorewww).
8. One same-machine benchmark covering MLX (Python and native), Core ML ANE, Core ML GPU, PyTorch MPS and the Rust Metal engines with pinned checkpoints and identical tokens. afshinm/laya-mps (M5 Pro) covers MPS plus two Core ML exports; nothing covers laya-mlx and the Rust engines alongside them. Giamme's harness (2026-09-28) targets this but has published no results.
9. Encode-once model (state encoded once, reused across questions). Requires retraining; kime's native models are announced, not shipped. abe238's CLM caches option encodings but is a different, 8B model.
10. ANE-validated English or typed-decisions checkpoint from FluidInference. Only laya-apple (BC1S graph, M4 Max) ships an ANE-correct typed-decisions artifact; its prebuilt artifacts are validated only for M4 Max / macOS 26 / coremltools 9.0, and every other Mac recompiles (about 4.5 min) and must self-calibrate.

## 7. Open questions

1. Base M5 ANE vs GPU crossover for the multilingual L128 bucket. On M5 Pro it is 3.6 vs 3.9 ms; on base M4 it is 14.5 vs 37 ms (typed-decisions, laya-apple). Where does the base M5 land? Nobody has measured it.
2. Does MLX's NAX attention kernel engage for head dim 64 with a boolean window mask (ModernBERT), or only the GEMMs? The PR trail suggests attention NAX paths are added per head dim and mask type.
3. Does a default mlx-rs build on macOS 26.2 include the NAX kernels? `mlx-sys/build.rs` sets no deployment target.
4. Core ML ANE latency on macOS 26.2 vs 27.0 for the same `.mlmodelc`. All FluidInference numbers are 27.0.
5. Is the 32 GB base M5 enough to hold two lineages side by side for a bake-off (MLX fp16 weights about 0.8 GB plus Core ML buckets 0.6 GB each plus compile caches)? Likely yes; peak numbers above suggest under 4 GB resident per runtime.
6. How much of laya-fast's 8x512 win (374 to 219 ms on M3 Max) survives on a base M5 where the GPU is smaller relative to the ANE? The split ratio comes from a per-machine cost model.
7. The TF32 default and the M5 padded-attention drift both break bit-parity tests. Which lineages' parity gates (mizorewww 0.02, FluidInference 0.02, laya-apple hard mismatch count) still pass on M5 with `MLX_ENABLE_TF32` left on?
8. FluidInference's English root on ANE fails at 0.035 on a 20-option low-temperature request. Would a W8 palette or the BC1S rewrite (laya-apple) recover it on M5-class hardware, and at what latency?
